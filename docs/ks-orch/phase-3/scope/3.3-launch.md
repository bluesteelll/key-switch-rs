### Tree facts the cut builds on (new since 7cb3521)

1. `Launch` and `OpenUrl` run on `action-executor`: `Win32Runner::action` at `src/core/executor/mod.rs:126-148` calls `launch_process` and `shell_open` (:131-132); macro steps go through `Runner::step` -> `sequence::run_step` (:150-152).
2. STA: `Apartment::enter_sta` calls `CoInitializeEx(None, COINIT_APARTMENTTHREADED | COINIT_DISABLE_OLE1DDE)` (mod.rs:377-392). It is balanced on the same thread (:395-403). A failure is a `[WARN]`, and the thread then runs without COM (:383-387).
3. The loop pumps (mod.rs:587-702). Its doc (mod.rs:582-586) says that a runner call can pump the queue ("a DDE or COM wait") and eat a `WAKE`, and drain-before-wait covers that case.
4. `pub trait Runner: Send + 'static` (mod.rs:115). `Win32Runner` is a stateless unit struct ("so a panic in one call leaves nothing behind", mod.rs:122-124). It is built on main (`src/core/app.rs:205`) and moved into the thread.
5. Every runner call runs under `catch_unwind` (`src/core/executor/runs.rs:119`, :195, :208).
6. `STOP_TIMEOUT` is 2 s (mod.rs:66). A step still running at stop leaves the thread to the end of the process (mod.rs:333-355). `QUEUE_CAPACITY` is 32 (mod.rs:62).
7. `TargetWindow::for_action` returns `NONE` for `Launch` and `OpenUrl`, so the firing thread makes no Win32 call (mod.rs:89-99).
8. Hook path: `dispatch` -> `as_fast()` is `None` -> `hook.submit` (`src/hook/keyboard_hook_callback.rs:326-334`; `src/hook/keyboard_hook.rs:104-106`; `ExecutorHandle::submit` mod.rs:217-238 does `try_send` + `PostThreadMessageW`).
9. The engine clones the bound action on the hook thread, under `with_main`: at fire (`src/engine/mod.rs:846`), when a gesture arms (`src/engine/gestures.rs:217-226`), and at chord and sequence arm (`src/engine/chords.rs:121`, `src/engine/sequences.rs:119`, :128). For `Launch` that clone allocates `exe`, the `args` Vec and every arg; `OpenUrl` allocates its String.
10. `as_fast` (`windows_actions.rs:187-206`) and `repeats_by_default` (:229-249) are exhaustive. Both send `Launch` and `OpenUrl` to the executor, with no repeat.
11. Schema: `RawAction::Launch { exe, #[serde(default)] args }` (`src/config/schema.rs:193-198`) and `RawAction::OpenUrl(String)`, a newtype (:199-201). `RawStep::Launch` is at :242-246 and `RawStep::OpenUrl` at :247. Both enums are `deny_unknown_fields` (:175, :235), so `cwd:` is a load error today. A loader test row pins that (`src/config/loader.rs:1553-1555`), and the book documents it (structure.md:199, actions.md:193).
12. The loader converts the actions at `loader.rs:716-721` and the steps at `:765-770`. `IMPLICIT_SOME` is on (`loader.rs:265`), so `cwd: "C:/x"` would deserialise into an `Option`.
13. The config path is `<exe_dir>\config.ron` (`loader.rs:98-107`).
14. `Cargo.toml:41-59` already has `Win32_System_Com` (:50), `Win32_System_Threading` (:57) and `Win32_Security` (:58). `Win32_System_Ole` and `Win32_System_Variant` are missing.
15. In windows 0.62.2, `IShellWindows::FindWindowSW` needs both `Win32_System_Ole` and `Win32_System_Variant` (`Win32/UI/Shell/mod.rs:43313-43314`). `IShellDispatch2::ShellExecute(&self, file: &BSTR, vargs: &VARIANT, vdir: &VARIANT, voperation: &VARIANT, vshow: &VARIANT) -> Result<()>` (`Shell/mod.rs:34946`). It takes **one** argument string and returns no process handle and no PID. `CLSID ShellWindows` (:56172), `SWC_DESKTOP` (:55807), `SWFO_NEEDDISPATCH` (:55811), `SID_STopLevelBrowser` (:55064) and `IServiceProvider::QueryService` (`System/Com/mod.rs:8790`) all exist.
16. Nothing in `src` reads the daemon's own elevation. A Grep for `TokenElevation|GetTokenInformation|OpenProcessToken|IsUserAnAdmin` finds no match.
17. The single-instance mutex is not inheritable, so a `Launch` child never keeps the name alive (`src/system/single_instance.rs:46-50`, KS-09 note of item 1.5).
18. The unreachable `SystemFunction::LockWorkstation` and `TaskManager` also start processes with `Command::spawn` (`src/system/system_function.rs:83-92`, :110-116).
19. The only `Win32Runner` test is ignored and opens a real URL (`mod.rs:1525-1538`).
20. Today's `exe` lookup follows Rust std rules: the daemon's folder, then System32, the Windows folder and the daemon's PATH. App Paths are not used. `.bat` arguments are checked by std (actions.md:186-192, errors.md:195-197).

## 4. Latency

**Key-to-decision path (hook callback and `Engine::on_key`):**

- Per-event work does not change. 3.3 adds nothing to the callback or the engine.
- The only cost on the hook path is the clone of a bound `Launch` or `OpenUrl` when it fires or arms (fact 9).
  - Today that clone makes 2 + n allocations for a `Launch` with n args, and 1 for an `OpenUrl`.
  - An inline `cwd: Option<String>` would add one allocation per fire when `cwd` is set.
  - Holding the launch spec behind an `Arc` makes the clone allocation-free (one atomic increment). That is a net cut on the key path, and it serves 3.4's acceptance ("With a counting `#[global_allocator]`, `Engine::on_key` does not allocate", roadmap.md:725) and the 2.1 hand-off "3.5: `Binding.action: Arc`" (results_v3.md:191).
- No lock is added. No Win32 call is added on the firing thread (`for_action` stays `NONE`, fact 7). `submit` does not
  change. There is no new timer, no change in timer resolution and no new wake-up of main or the watchdog.

**Action latency (key to program start), on the executor:**

- Today: an in-process `CreateProcessW` (`Command::spawn`) or an in-process `ShellExecuteW`.
- On the roadmap's route each launch adds about 6-7 cross-process COM calls into Explorer's desktop thread before
  Explorer does its own `ShellExecute`: `CoCreateInstance(ShellWindows)`, `FindWindowSW`, `QueryService`,
  `QueryActiveShellView`, `GetItemObject`, `Application`, `ShellExecute`. BSTR and VARIANT allocations come on top,
  which is allowed off the hook path. The tree has no measurement of this cost (UNVERIFIED).
  - A busy Explorer UI thread adds its own delay.
  - A hung Explorer blocks the executor, and so every queued macro, until it answers.
  - `swch exit` stays bounded by `STOP_TIMEOUT` (fact 6).
- Caching `IShellDispatch2` would save the lookup calls, with two constraints. It needs a thread-local on the executor
  thread, because the windows crate's COM interfaces are not `Send` and `Runner: Send` (fact 4). It also needs
  stale-proxy handling after Explorer restarts. Fork for the architect.

**Bench rows:**

- None of R1-R18 runs `Win32Runner` or a `Launch` binding (`src/bench.rs:22-95`; R6 uses `FakeRunner` and a macro,
  bench.rs:837-878), so none should move.
- **New R19 (gating):** the key-down callback of F13 bound to `Launch(exe: "x.exe", args: [3 args], cwd: ...)`, with a
  `FakeRunner` executor attached. It runs on P and H. It pins the clone plus submit, and H <= P with the `Arc`.
- **New R20 (diagnostic, evidence for F-a):** the Explorer lookup chain alone, up to `IShellDispatch2` with no
  `ShellExecute` call and no process started, p50 and p99. The calls only read state from Explorer; the row needs an
  interactive desktop, so it is `bench:`-ignored like the others.

## 7. Size and split

**M, one lane.** The work is:

- one new module (about 300-450 lines with tests, an estimate);
- 37 construction and match sites in 8 files;
- two schema variants;
- one loader test row to flip;
- docs on four config pages.

The risk of L comes from the COM chain: how errors surface (an HRESULT only, no PID), Explorer missing or hung,
argument quoting, and Q3 = yes, which needs a second `OpenUrl` form in the loader.

Do not split. The default `elevated: false` makes sense only together with the de-elevated route. Both halves edit the
same variants, Display arms and doc pages, and a split would ship two breaking changes to the same fields. If a split
is forced, the only clean cut is lane A (KS-34: own console, `cwd`, through `Command`, without COM) followed by lane B
(Explorer route, `elevated`). That is not recommended.

## 8. Questions for the owner (values or scope)

1. **Open question 3: uiAccess deployment** (roadmap.md:942). Recommendation: **keep `requireAdministrator`, with no
   code signing for now, and run 3.3 as planned.**
   - The route can be chosen at run time from the daemon's own token, so a later uiAccess deployment needs no rework
     of 3.3, and the Explorer route stays useful under uiAccess too: children of a direct spawn would carry the
     daemon's token (UNVERIFIED for the uiAccess flag; research-3.3.md).
   - Evidence: build.rs:32-34, app.manifest:9-18; no signing or release packaging (roadmap.md:857, gaps.md:240).
2. **What `elevated: true` does: start silently with the daemon's administrator token, or ask for a UAC prompt each
   time (the `runas` verb through Explorer)?** Recommendation: **prompt.**
   - `config.ron` lives next to the executable (loader.rs:98-107), and 4.4 moves it to `%APPDATA%`, where code at
     medium integrity can write. A silent opt-in lets any such writer add `elevated: true` and get admin code without
     a prompt (build-and-run.md:312, audit.md:337).
   - With the prompt, everything goes through Explorer, and nothing runs as administrator without consent, which
     extends roadmap.md:935.
   - Cost: one UAC prompt per elevated launch. On the secure desktop that prompt also triggers 2.3's input-left reset.
   - If you choose silent, the research report has the prior art (AutoHotkey, PowerToys; UNVERIFIED here).
3. **Does `OpenUrl` get `elevated:`?** Recommendation: **no, `Launch` only.** Reword acceptance line 3 to
   ``Launch(exe: "cmd.exe", args: ["/k", "whoami /groups"], elevated: true)` reports `High Mandatory Level` ``.
   - The syntax plan names only `Launch` (roadmap.md:871).
   - `OpenUrl` is a RON newtype (schema.rs:199-201, :247), so the opt-in needs a second syntax form.
   - Chromium browsers de-elevate themselves (audit.md:337), so "with `elevated: true` it is" cannot be shown with
     Edge or Chrome.
4. **The working directory when `cwd:` is absent.** Recommendation: **the user's profile folder, as the Run dialog
   gives (UNVERIFIED).**
   - The alternatives are the program's own folder, or Explorer's current directory (likely System32, UNVERIFIED),
     which repeats KS-34's System32 problem (audit.md:667).

**Technical forks: my recommendation for the architect, not owner questions.**

- T1 route.
  - Option 1, the roadmap's shell dispatch: needs Ole and Variant, joins the args into one string, returns no PID.
  - Option 2, `CreateProcessW` with `PROC_THREAD_ATTRIBUTE_PARENT_PROCESS` set to Explorer: only features that exist

  - Recommendation: the roadmap's route, unless research-3.3.md finds a blocker. The cut must say how a missing
