# Scope: roadmap item 3.1 "Single input module" (Phase 3)

Read on `master` = `252daef` (work tree on `docs/book-2.5`, `src/` identical). Book, README and CHANGELOG read with
`git show 252daef:<path>`. No cargo command was run; nothing was built, injected or installed. Confidence marks:
**verified** (read in the tree), **UNVERIFIED** (inferred, needs a check), **doc** (Microsoft Learn or AutoHotkey
documentation, sources at the end).

Verdict in one line: 3.1 is two lanes, about L in total (the roadmap says M). Lane A builds the module, scan codes,
`Text` newlines and the mask in one call, with no change to engine semantics. Lane B handles the modifiers held around
output (KS-19, known issues 30/35/68/75), the restore race, and optionally known issue 66 and the per-press mask.

## 1. Re-location

### 1.1 The item as written (roadmap.md, `252daef`, lines 674-684)

- **What.** One module is the only caller of `SendInput`. A pure `build_inputs(payload, held_mods)` releases the
  modifiers that reached the OS, sends the payload, restores the physically held modifiers, and adds the `0xE8` mask
  after Alt or Win. `wScan` comes from `MapVirtualKeyW(MAPVK_VK_TO_VSC_EX)`. `KEYEVENTF_EXTENDEDKEY` is set for the
  arrows, Ins, Del, Home, End, PgUp, PgDn, RCtrl, RAlt, Win and Apps. In `Text`, `\n` becomes Enter and `\t` Tab.
- **Why.** KS-19 (synthesized keys combine with held modifiers). KS-36 (no scan code, unverified). Three builder
  copies, with five `SendInput` calls in three files.
- **Files.** New `src/platform/input.rs`, plus `core/windows_actions.rs`, `data/sequence.rs` and
  `system/system_function.rs`.
- **Acceptance.** `rg "SendInput\(" src` finds one place. `(Left, [LAlt])` builds LAlt up, Left down (extended),
  Left up (extended), LAlt down, E8 down, E8 up. `Alt+J -> PressKey("Left")` moves the cursor in Notepad.
- **Status after Phase 1** (roadmap.md:684). Item 1.2 added a fourth builder, `menu_mask_inputs`, and four Phase 1
  follow-ups name this item.

- **Fast actions run on the main thread; `Launch`, `OpenUrl` and `Sequence` run on the executor** (2.1):
  `windows_actions.rs:118-166` and `:182-206`, `keyboard_hook_callback.rs:326-334`. A Hold or a waiting Tap is carried

- **The test seam exists in part.** Under `cfg(test)`, `FastAction::run` only records (`windows_actions.rs:148-180`)
  and `send_menu_mask` only counts (`keyboard_hook_callback.rs:380-392`). They keep two separate records, so nothing
  can pin their relative order. That gap is follow-up M14 of 1.2.

### 1.4 Moot or drifted

- **"three copies ... five calls in three files"** is stale: there are now four builder sites and six calls
  (§1.2). It is drift, not moot.
- **KS-19's second half is mostly moot:** "`press_combo` ... sends key-ups for modifiers the user is physically
  holding, after which `sync_modifiers` reads them as up and the hook's state diverges". `sync_modifiers` is gone (no
  match in `src`; 2.5 replaced it with `resync_modifiers` on main, `keys.rs:96-116`). Since D2 the engine follows the
  injected key-up of a sided modifier. A generic code such as Combo's `VK_CONTROL` (`parsing.rs:18-32`) clears only
  the generic slot. The sided slot is then dropped by the next key-down's check (`keys.rs:118-143`), so the engine
  catches up one event later. The release itself (known issue 35) remains.
- **KS-36's text lists NumLock among the extended keys.** Microsoft Learn says Num Lock "is not considered an extended
  key despite appearing in the extended key name table". The same page's scan table gives NumLock as `0x0045` and as
  `0xE045` "as seen in legacy keyboard messages" (doc). Findings in audit.md stay as they are; this goes into the
  KS-36 status line only.
- **The roadmap's extended-key list is incomplete against Microsoft's.** Microsoft also names Print Screen, Break
  (Ctrl+Pause), and numpad Divide and Enter. Its scan table also gives `0xE0`-prefixed codes for the consumer (media)
  keys, for example Volume Increment `0xE030` and Play/Pause `0xE022` (doc).
- **The roadmap's Files line is incomplete.** It lacks `hook/keyboard_hook_callback.rs` (mask builder, `carry_out`),
  the engine (the held set: see §3) and `core/executor/mod.rs` (macro key steps).

All of the What: the module, the only `SendInput`, scan code and extended flag, `Text` newline and tab, the release
and restore around output, the masks, and the three acceptance lines. Section 2 adds the follow-ups.

## 4. Latency (the owner's top priority)

Evidence base: 2.5 bench (`p2-2.5-latency-trim/results.md:102-111`):

| Row | What | p50 |
| --- | --- | --- |
| R12 | ordinary key | 0.2 µs |
| R11 | swallowed key-up with witness | 0.8 µs |
| R17a | one `GetAsyncKeyState` | 0.545 µs |
| R18 | 8 modifier reads on main | 4.5 µs |

2.1 measured the early passes plus the timing at about 63 ns per event (`p2-2.1-executor/results_v2.md:60`). The bench
runs under `cfg(test)`, where `FastAction::run` only records (`windows_actions.rs:148-151`), so **no bench row
executes a `SendInput` today, and none can** (the safety rules forbid injection). The OS-side cost of an injected
event (kernel transition, every low-level hook in the chain) is **unmeasured**.

### Lane A

- **Per-event work for events that fire no key action:** unchanged (R1, R4, R11, R12 and R12m should not move).
- **A `PressKey`, `Media` or `ToggleCapsLock` that fires:** the same 2 injected events. Scan code and flag come from
  a table filled once on main (T4): an index, no Win32 call. Looking up `MapVirtualKeyW` per press would add one user32
  call per press, of unmeasured cost (UNVERIFIED; a probe row R19v settles it).
- **A masked decision whose first action injects keys:** one `SendInput` instead of two, the same number of events.
- **Allocations:** none on the hook path, if the batch is a fixed-capacity stack array; the worst case of lane B is
  about 22 `INPUT`s of 40 bytes. `Text` and `Combo` still allocate on the executor, which is off the hook path.
- No locks, no timers, no wake-ups, no change to timer resolution.

### Lane B

- **Events that fire nothing:** unchanged, if the held set is computed only when the decision fires an action that
  injects keys. Even computed always, it is about 11 flag reads.
- **Source of the held set on main (T1).** The engine's records, no OS read. With `GetAsyncKeyState` on the 8 sided
  modifiers it would cost about 8 × 0.545 = 4.4 µs per key action in the callback (R17a, R18), and CLAUDE.md rule 1
  forbids new key-state reads there beyond what a cut prescribes.
- **A key action with k modifiers down in Windows:** +2k injected events (release and restore), plus up to 4 mask
  events when Alt or Win is among them.
  - Daemon work: each event re-enters the callback on the sentinel path, about 0.06-0.1 µs (2.1 figure, plus D2's
    10-20 ns `track_injected`).
  - OS cost: unmeasured. It delays the payload by the k release events ahead of it.
  - Example, Alt+J -> Left: today 2 calls and 4 events (mask, Left); after B, 1 call and 8 events.

## 8. Questions

### 8.1 For the owner (values or scope)

1. **No opt-out from the release?** After lane B, every key output ignores the modifiers the user holds
   (`Shift+F9 -> PressKey("A")` types `a`). Should a binding be able to keep them, as AutoHotkey's `{Blind}` mode
   does? **Recommendation: no opt-out in 3.1;** Q2 gives the explicit form. Evidence: KS-19 classes today's behaviour
   as a defect, and the roadmap acceptance asks for the release. AutoHotkey's default Send releases held modifiers,
   and Blind mode is the exception that "avoids releasing the modifier keys ... if they started out in the down
   position" (doc). Microsoft notes that held keys "might interfere with the events that this function generates"
   (doc).
2. **`PressKey("Ctrl+S")`, a combination on the fast path?** This is additive syntax, about S in lane B: the payload
   of a batch is a list anyway. **Recommendation: yes.** It is the migration path for users who relied on the
   combining, at the lowest latency. Today the only explicit form is `Sequence([Combo("Ctrl+S")])`, which goes through
   the executor's queue and thread wake (2.1, `keyboard_hook_callback.rs:326-334`).
3. **Known issue 66 inside 3.1?** **Recommendation: yes for `Tap` and `Hold` on a lone Alt or Win.** For `DoubleTap`,
   leave the first tap a real lone tap for Windows and document it, with `block_default: true` as the workaround,
   because the daemon cannot know at the first release whether a second press will come. Evidence: the follow-up names
   3.1, roadmap.md:425 says "no item yet", and AutoHotkey documents the same remedy for its pass-through Win hotkeys
   (`~LWin::Send {Blind}{vkE8}`, doc).

### 8.2 Technical forks (the architect decides; recommendations with evidence)

- **T1, held set on main.** Use the engine's records (`keys.rs:298-309` generalised to `SIDED`), carried in the
  `Decision` and computed under the borrow. Not `GetAsyncKeyState` (§4). Residual: a modifier the hook could not see
  (known issue 88) can still combine. Declare it.
- **T2, the event's own key.** At a key-down that passes, Windows does not have the key down yet: the engine has
  already run `press()` (`engine/mod.rs:767`), and Windows applies the event after the hook returns
  (`keyboard_hook_callback.rs:108-113`). So the own key is left out. At the key-up of a passed key, Windows still has
  it down (the engine has already run `release()`, `:963`), so the own key is put in. This is what makes an `LCtrl`
  `Tap` -> Escape fire without Ctrl.
- **T3, executor.** Read the 8 sided modifiers with `GetAsyncKeyState` before each key step, on the executor thread.
  Not a snapshot taken at submit, which goes stale after a `Delay`.
- **T4, scan codes.** Build a table once on main at startup with `MapVirtualKeyW(MAPVK_VK_TO_VSC_EX)`, so a press
  makes no Win32 call; R19v provides the evidence. Residual: `MapVirtualKey` uses the calling thread's layout (doc:
  "To specify a handle to the keyboard layout ... use MapVirtualKeyEx"). A letter's scan code therefore follows the
  daemon thread's layout, which matters only for layouts that move letters (AZERTY, QWERTZ). Russian/English keep the
  US positions (UNVERIFIED). Declare it.
- **T5, extended flag.** Derive it from the `0xE0` high byte. Do not hand-list the keys: Microsoft's list is longer
  than the roadmap's (§1.4). Send `0xE1` (Pause) without the flag. Pin both with tests.
- **T6, mask placement.**
  - Put E8 **before** releasing an Alt or Win (merged with the decision's mask), and **after** restoring one.
  - The roadmap's acceptance line omits the leading mask. A modifier-only passing `LAlt` `Hold` fires from a timer,
    and a timer decision never masks (`engine/mod.rs:245`), so without the leading E8 its release would be a lone Alt
    tap.
  - Refined line: `E8 down, E8 up, LAlt up, Left down (ext), Left up (ext), LAlt down, E8 down, E8 up`.
  - Whether a trailing E8 should also follow a restored Ctrl or Shift, against lone-tap detectors, is settled by the
    manual check in §5.
- **T7, mask per press.** Adopt AutoHotkey's rule (§2, F3).
- **T8, `Media`.** Do not release for media keys. They repeat by default (owner decision), and the KS-12 verification
  found that an injected media key under Alt works and even masks Alt (audit.md KS-12 "Verification"). This saves
  4-6 events per repeat. If the cut releases them anyway, a manual check decides.
- **T9, the restore race.** This is the key risk.
  - **Main thread.** The decision and the `SendInput` happen with no pump in between. Injected events are delivered
    to this hook re-entrantly inside `SendInput` (`keyboard_hook_callback.rs:94-107`). A physical key-up whose hook
    call is pending is therefore applied after the batch, so it is safe, except when Windows timed that call out
    (`LowLevelHooksTimeout`). UNVERIFIED Windows internals.
  - **Executor.** The user can release a modifier between the read and the batch, or while the batch waits for main.
    The restore then leaves the modifier **stuck down** in Windows.
  - **Recommendation:** a guard in the hook. A restore event can be told from other injections (for example a second,
    PID-mixed marker next to the sentinel, which changes R2's "one constant, one comparison" and needs the reviewer's
    agreement). The guard swallows a restore whose physical key-up the engine has already decided. Pin it with a
    scenario.
  - Never prefer "stuck" over "lost".
- **T10, `ToggleCapsLock` and Shift.** Under "Press the SHIFT key" to turn Caps Lock off, an injected Shift restore may
  turn caps off again (UNVERIFIED). Fallback: for `ToggleCapsLock`, release Shift and do not restore it. The user is
  releasing Shift+CapsLock anyway. The manual check decides.
- **T11, `Text` controls.** `\n`, `\r` and `\r\n` each become one Enter, and `\t` becomes Tab, as AutoHotkey's Text
  mode does (doc). `Text` also releases held modifiers in lane B (UNVERIFIED that held Ctrl affects
  `KEYEVENTF_UNICODE`; the release is the safe side).
- **T12, test seam.** Keep `FastAction::run` record-only under test (CLAUDE.md rule 9). Under `cfg(test)`, the
  module's send records the built batch instead of calling `SendInput`, in one ordered thread-local log shared with
  the action record.
