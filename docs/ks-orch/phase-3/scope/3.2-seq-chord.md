### 1.5 What remains

**R1. KS-15: trigger-key rule for steps.**

- Today a step counts when its keys are held at any key-down (`sequences.rs:91`, `:114`).
- `book/src/config/kinds.md:74` (§8.2 item 2) documents this as "a subset test: the pressed key does not have to belong
  to the step".
- Fix direction: pass the event's `vk` into `Sequences::on_key_down`. A step counts only when `vk` is one of its
  trigger keys and its keys are held. This is the combo rule `matching::is_trigger_key` + `keys_down`
  (`src/engine/matching.rs:52-67`), or `matching::combo_matches` (`:74-83`) under Q1.
- The same rule applies to the fresh start, which closes the second symptom of KS-15 as well: with `["F13","F14"]` and
  F13 held, every unrelated key re-arms the sequence and is swallowed (`kinds.md:97`).

**R2. KS-16: modifier wait.**

- While an entry waits for step N, a key-down of a modifier that step N names (Ctrl for `Ctrl+S`; any key of a
  modifier-only step) neither aborts nor advances the entry. The modifier's key-down passes.
- Today it aborts (`sequences.rs:108-110`). A pass is what the acceptance needs ("Ctrl's key-up reaches the OS"): a key
  whose key-down passed has its key-up pass (`mod.rs:981-999`).
- Auto-repeats of the held modifier already skip sequences (`mod.rs:860`), so a held Ctrl's repeats cannot abort.
- The design forks are T1 and T2 in §8.

**R3. F1: `mark_completed` records a held key with no record as swallowed.**

The roadmap row is `roadmap.md:991`, from the 2.3 cut F1 (`<orch>/p2-2.3-control-window/cut.md:857`). It is
the same defect as A3's Deviation 6 (`<orch>/p0-A3-suppression/impl.md:123-125`).

Finding (verified by reading, every path traced by hand): `mark_completed` (`keys.rs:254-261`) changes a record only
when the key is held and its record is `Unknown` or `RepeatSuppressed`. Where a record is already `Suppressed`,
writing `Suppressed` changes nothing. Such a held key exists only when the engine never saw the press's key-down,
which means Windows has the key down:

- Every decided key-down ends with a record: `mark_blocked`, `mark_passed`, or the repeat branch (`mod.rs:940-956`).
- `resync_from_os` records every held key as `Passed` (`keys.rs:181-202`).
- `release_all` frees every key (`keys.rs:209-211`).
- A held key with no record comes only from the drain read of the sided modifiers (`resync_modifiers`, `keys.rs:104-116`)
  or from the daemon's own injected modifier events (`track_injected`, `keys.rs:150-159`).

Three consequences follow:

- (a) For sequences, `last_step_keys` holds non-modifier codes only (`sequences.rs:156-170`), so `mark_completed`
  changes nothing.
- (b) For the completing key it changes nothing either, because the tail's `mark_blocked` runs after it (`mod.rs:949-950`).
- (c) For chords it acts only on a modifier chord key that was pressed (and swallowed) for the chord, released, then
  pressed again unseen and read by the drain, all inside the window. That is exactly F1.

The visible effects of F1:

- the modifier's auto-repeats are swallowed while Windows has it down (`mod.rs:940-941`);
- `alt_or_win_down_in_windows` skips it, so a later swallowed key under that Alt or Win gets no menu mask
  (`keys.rs:304-309`);
- the drain read and the check both skip it (`keys.rs:107`, `:137`), so a later unseen release leaves a phantom
  modifier held for exact matching.

Its key-up still passes through the witness (`mod.rs:999`).

Fix direction: delete `mark_completed`, the `last_step_keys` and `keys` fields of the two `Completed` outcomes
(`sequences.rs:57-60`, `chords.rs:62`) and the two loops (`mod.rs:885-887`, `:911-913`). Each key's own key-down
record already says whether its key-up is swallowed. The lane confirms this with a mutation run: with the calls
removed, every test stays green except `keys::tests::completion_marks_only_held_keys_whose_key_down_did_not_pass`,
which tests the function itself. The F1 red-first test then turns green. If the architect prefers to keep a guarded
function, its predicate becomes "record is `Suppressed`", which makes it a no-op. Deleting it is simpler.

**R4. `when:` after the match for `sequence` and `chord`.**

- Both kinds evaluate the condition first, on every non-repeat key-down (`mod.rs:860`, `:892`).
- The title of a `TitleContains`/`TitleEquals` is read live, at most once per event, with one `GetWindowTextW` and a
  `String` (`src/hook/keyboard_hook_callback.rs:182-218`).
- Chord: test membership (`chords.rs:81-83`, pure) before the condition.
- Sequence: evaluate the condition only when the key-down can change the binding's state. With nothing pending, that is
  a trigger key of step 0. With an entry of its shape pending, every non-repeat key-down counts, because it advances,
  waits or aborts. This keeps the documented rule "`when` false: the pending entry neither advances nor resets"
  (`kinds.md:82`, §8.2 item 10).
- 3.5 names this rule (`roadmap.md:737`, `:739`). §8 T4 gives the reasons for moving it into 3.2.

**R5 (owner Q1). Exact modifiers on steps**, and `allow_extra_modifiers` accepted on `sequence`. A2 deferred this to
3.2 explicitly (`<orch>/p0-A2-matching/cut.md:115-121` and `:518-519`, Q3; `loader.rs:489-491`).

**R6 (owner Q2). Shared-shape defects.** Two cases, both derived from the code:

- Two `sequence` bindings with identical steps and conditions that both hold share one entry
  (`sequences.rs:89`, `p.steps == steps`).
  - With `["F13","F13"]` the second binding completes the entry that the first one started, on the **same** key-down,
    so the first binding's action fires after a single press (known issue 19,
    `book/src/config/known-issues.md:51`; `kinds.md:91`).
  - With `["F13","F14"]` the second binding aborts that entry and restarts it with its own action. That contradicts
    the module doc "the action of the binding that started it fires" (`sequences.rs:8-10`; gaps.md "No longest match"
    row, `gaps.md:165`).
- For chords with the same key set, the completing key-down opens a new attempt for the second binding (`kinds.md:146`,
  §9.2 item 8; `chords.rs:91-125`).

**R7. Bookkeeping.**

- Name the existing chord tests against the acceptance line (§1.3).
- The two sequence repro tests (source in `book/src/methodology.md`, "Gesture repro crate"; the crate itself is not on

  `Sequences::on_key_down(vk, &held, ...)` with the sided `VK_LCONTROL` that the hook reports (the repro used the

### 3.3 Config and RON changes, and compatibility

- **No new field and no syntax change.** Every config that loads at 252daef still loads.
- **Behaviour fixes.** KS-15: rollover no longer completes a step, and an unrelated key no longer re-arms. KS-16: a
  named modifier pressed after the previous step no longer aborts. Neither is breaking in syntax. A config that relied
  on rollover completing a step is implausible.
- **Q1 = yes.** Breaking. A step no longer matches while a modifier it does not name is held. Example: `["F13","S"]`
  with Shift held types a capital S instead of firing. With `["F13","Ctrl+S"]`, Ctrl+Shift+S (Save As) reaches the
  application. `allow_extra_modifiers: true` on a `sequence` turns from a load error into a loading field, which is
  non-breaking. CHANGELOG `Changed` with a **Breaking** line.
- **Q2 = yes.** A behaviour fix. Duplicated shapes fire the first binding's action once.
- **R4.** The `when:` order changes no outcome. It is a latency change only (§12.4 of `triggers-conditions.md`).

## 4. Latency

The owner's top non-functional priority is the key-to-action path. 3.2 only removes work from it.

**Per-event work on a non-repeat key-down.** Today each `sequence` binding runs:

- `condition.evaluate` (`mod.rs:860`);
- `ids.next_seq()` (`:863`);
- `retain` (`sequences.rs:86`);
- `position` with a `Vec<KeyCombination>` comparison (`:89`);
- `keys_down` on step 0 (`:114`).

After 3.2, the first test is whether `vk` is a trigger key of step 0, or of the next step when an entry is pending.
That test is a scan of a few `KeySpec`s (`matching.rs:62-67`). Ordinary typing stops there: no condition, no `retain`,
no lookup. Chords already test membership first inside `on_key_down` (`chords.rs:81-83`), but the condition runs before
it (`mod.rs:892`). After 3.2 it runs after it.

**Win32 calls.**

- None is added.
- A `sequence` or `chord` with a title `when:` today reads the title (`GetWindowTextW`) on **every** non-repeat
  key-down system-wide (`keyboard_hook_callback.rs:213-217`, `HookEnv::foreground_title`).
- Measured at item 2.3: R10 (a `TitleContains` key-down) has a median of about 6.5 µs against 4.8 µs for an unbound key
  (R12) (roadmap open question 12, `roadmap.md:951`). The title read thus costs about 1.7 µs per key.
- After R4, only the binding's own trigger keys pay it, plus every key-down while an entry is pending.
- `AppEquals` reads only the main thread's cache (`keyboard_hook_callback.rs:209-211`), so it saves less.

**Allocations.**

- None is added.
- Removed: the title `String` (`OnceCell<Option<String>>`, `keyboard_hook_callback.rs:184`) on unrelated keys, and one

## 8. Questions and forks

### Owner questions (values and scope)

**Q1. Do sequence steps match modifiers exactly, like `keys` bindings, with `allow_extra_modifiers: true` then
allowed on `sequence`?** Chords keep matching whatever modifiers are held.

- Recommendation: **yes**.
- Evidence: the owner decision "exact modifier matching, with a per-binding `allow_extra_modifiers`" (CLAUDE.md). The
  argument that carried it (open question 2, `roadmap.md:941`: Ctrl+J must not swallow Ctrl+Shift+J) applies to a step
  the same way: `["F13","Ctrl+S"]` would otherwise swallow Ctrl+Shift+S (Save As).
- A2 deferred exactness on steps to 3.2 on purpose (`p0-A2-matching/cut.md:115-121`, `:518-519`; `loader.rs:489-491`).
  Its stated reason was that relaxing later is non-breaking, while giving an accepted field meaning later is a silent
  change.
- Cost: a **Breaking** CHANGELOG line. A step no longer fires while an unnamed modifier is held: `["F13","S"]` with
  Shift types a capital S. Two scenarios are rewritten (§3.1).
- Chords stay as they are. "Unrelated keys do not interfere: Ctrl+F13+F14 also fires" (`kinds.md:144`), and their keys
  are single keys, which modifiers may be.

**Q2. When two `sequence` (or `chord`) bindings with the same steps (key set) both have a `when:` that holds, should
the first in file order fire once (one key-down feeds one shape once), instead of today's behaviour?** Today a single
press of `["F13","F13"]` fires, the later binding's action wins for `["F13","F14"]`, and a chord re-arms on its own
completing key.

- Recommendation: **yes, in 3.2**. It is S: a per-event mark in `Sequences` and `Chords`, with no allocation.
- Evidence: known issue 19 (`known-issues.md:51`), `kinds.md:90-91` and `:146`. The module doc already promises "the
  action of the binding that started it fires" (`sequences.rs:8-10`). The 1.6 principle is one winner per press, and
  the loader already warns about exact duplicates (`errors.md:182`). The warning does not fire when the conditions
  differ but both hold.
- Alternative: defer to 3.4 or feature 8, and keep the documented warning.

### Technical forks (decided here; the architect may overrule with evidence)

- **T1. Which key-down keeps a pending sequence waiting, and does it pass?**
  - Recommendation: only a **modifier that the next step names** keeps the entry waiting (for a modifier-only step:
    any of its keys that does not complete it), and that key-down **passes**.
  - A non-modifier of the step pressed without completing it (F14 of `"F14+F15"`, or F14 of `"LShift+F14"` with RShift
    held) aborts, as today.
  - Why:
    - It is the KS-16 report and the audit's suggested fix ("typically its modifiers", `audit.md` KS-16), and the
      roadmap's "usually its modifier".
    - The acceptance needs Ctrl's key-down to pass.
    - A waiting key-down never needs swallowing, so a failed sequence loses nothing more (the replay scope of
      feature 5).
    - A non-modifier pressed alone stays a typed key, as in every other kind (the trigger-key rule, KS-04).
    - It keeps `sided_shift_in_a_sequence_step_matches_only_its_side` (`scenarios.rs:1396-1406`: RShift+F14 passes)
      and the `["F14+F15","F14+F16"]` scenario (`:3481-3502`) green.
  - Cost: a later step with two non-modifier keys still needs its first key held from before. That is the same as
    today; document it.
  - Under Q1 = no (superset), an unnamed modifier also neither aborts nor advances, since it does not stop the step
    from matching. Under Q1 = yes it aborts.
- **T2. Does a waiting key-down move the deadline?** **No.** The gap stays between step key-downs that advance the
  entry (`kinds.md:76`, §8.2 item 4), and no timer is asked for. That is simple, and it keeps 2.2's token discipline
  (F-l). The user can raise `max_gap_ms`.
- **T3. F1: delete `mark_completed`** and the outcome key lists (§1.5 R3), rather than restrict it.
- **T4. `when:` after the match belongs to 3.2, not 3.5.**
  - It is the same lines (`mod.rs:857-916`) and the same tests; splitting them across two lanes and two phases would
    rewrite the arms twice.
  - It is a pure latency win on the owner's top priority (§4), so it should not wait for 3.4.
  - The sequence rule keeps `kinds.md:82`: the condition is asked for a trigger key of step 0, or for any key-down
    while the binding's shape is pending.
- **T5. Pending-entry identity stays the shape** (steps, key set). No binding index in 3.2: the allocation-free
  `on_key` is 3.4's.
- **T6. One predicate.** Steps use `matching::combo_matches` (Q1 = yes) or `is_trigger_key && keys_down` (Q1 = no).
  There is no second rule next to the `keys` one, so RC1 is removed for sequences by construction, as 3.4 wants.
