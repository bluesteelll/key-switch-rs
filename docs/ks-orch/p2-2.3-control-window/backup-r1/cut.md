## Goal and non-goals

**After the lane.**
1. The main thread owns a hidden top-level control window (not `HWND_MESSAGE`). `WM_WTSSESSION_CHANGE` (registered with `NOTIFY_FOR_THIS_SESSION`), `WM_QUERYENDSESSION` and `WM_ENDSESSION` reach it; a second WinEvent hook, `EVENT_SYSTEM_DESKTOPSWITCH`, sits next to the foreground hook. Every class, window, registration and hook is released by a Drop guard or by `uninstall`.
2. `MainState::reset_transient_state(hook, reason)` drops every pending gesture, chord, sequence and owed mask, starts a new timer generation, cancels macros through `KeyboardHook::cancel_actions`, and resyncs keys by the rule of D1. It runs, always on the main thread between two events, on `swch off`/`on` (`RemappingSwitched`), on a reload (`Reloaded`, through a `Request::Reload` that also swaps the list), on `WTS_SESSION_UNLOCK` (`SessionUnlocked`) and on `EVENT_SYSTEM_DESKTOPSWITCH` (`DesktopSwitched`).
3. A foreground change never forgets a swallowed key-down (D2). Rule L: while remapping is on, the key-up of a key whose key-down was swallowed is swallowed, across focus changes, reloads, resets and `swch on`.
4. After Win+L (or any lost-input reset) the next press of a swallowed key fires (D3); a passed key is re-read from the OS.
5. The executable name of the foreground window is cached per (HWND, pid), filled in the foreground callback and at resets and startup; the hook path never queries a process. The title is read live, at most once per key-down that evaluates a title condition, with `GetWindowTextW` on the cached HWND (D9).
6. The 2.2 leftovers m2, OQ3, P1, OQ2, the executor doc line and the watcher `.expect` land as separate commits.

**Non-goals** (later items): `TaskbarCreated` and the tray (4.6; follow-up F2); the Raw Input watchdog on this window (2.4); `when:` after the match for `sequence`/`chord` and the 100 µs budget (3.5); a `swch reload` command (4.3); repairing a lost key-up that no reset follows (row 63 says so); the lone key-up while remapping is off (row 59, unchanged: the off path reads no event).

**Items that depend on this one:** 2.4 (Raw Input `RIDEV_INPUTSINK` needs this window), 4.2 (background mode uses `WM_ENDSESSION`), 4.6 (the tray lives on this window).

## Decisions

### D1: One reset, four reasons; the key rule per reason
**What.** In `engine` (pure):
```rust
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
pub enum ResetReason { RemappingSwitched, Reloaded, SessionUnlocked, DesktopSwitched }
impl ResetReason { pub fn may_have_lost_key_events(self) -> bool /* false only for Reloaded */ }
impl fmt::Display for ResetReason // "remapping switched" | "config reloaded" | "session unlocked" | "input desktop switched"
impl Engine { pub fn reset(&mut self, env: &dyn Env, reason: ResetReason) }
```
`Engine::reset` always: `gestures.clear()`, new `Chords`/`Sequences`, `mask_owed = false`, `ids.generation += 1` (wrapping). Keys only if `reason.may_have_lost_key_events()`, through `KeyState::resync_from_os(env)` (replaces `reset_from_os`, `keys.rs:122-135`), per code 1..=254 except the five mouse buttons:

| OS reports the code down | record before | after |
|---|---|---|
| yes | any | held, `Passed` (Windows saw a key-down; its repeats and key-up must reach it) |
| no | `Suppressed` | **not held, `Suppressed` kept**: the next key-down is a first press (fires), a key-up still due is swallowed (rule L) |
| no | `Passed`/`Unknown` | not held, `Unknown` |

`Reloaded` leaves the key table as it is.
**Why.** A reload loses no key event, so the OS view adds nothing; reading it races the async-state update of a key-down that just passed ("the state of the key being delivered lags until the hook returns", `src/engine/env.rs:36-38`): a passed held key read as up becomes a first press on its next repeat, which a binding may swallow, and its key-up then stays swallowed while Windows has the key down (stuck key). For the three lost-input reasons the OS is the only witness for keys Windows saw; for swallowed keys it is no witness at all (KS-14), so their record survives and only `active` is cleared, which is what makes the next press fire (owner decision, open question 9) while a key-up that does come is still swallowed.
**Rejected.** (a) Today's `reset_from_os` for every reason: forgets swallowed records, so a swallowed key held across `swch on` or an unlock gives Windows a lone key-up. (b) Keep `active` for swallowed keys at an unlock: the next press stays a repeat (known issue 63, against the owner decision). (c) Resync passed keys on reload: race above. (d) The spec's literal "resync all 256 keys" on reload: same race; Question 2.
**Cost.** ≤ 254 `GetAsyncKeyState` per lost-input reset (rare events; `swch on/off` already pays it). Nothing per key event.

### D2: A foreground change resyncs modifiers and forgets nothing (rule L)
**What.** `Engine::on_foreground_changed(env)` = `keys.sync_modifiers(env, None)` only. `LastDown::Forgotten` and `KeyState::forget_blocked` are removed (`keys.rs:66-70`, `:213-223`); `key_down_swallowed` (`keys.rs:139-144`) becomes `== Suppressed`. Applies to every daemon, elevated or not.
**Why.** In the current engine a swallowed record is consulted only by its own key's repeats and key-up. A lost key-up leaves `active` set (`keys.rs:146-153`), so the next press reads as a repeat whatever the record says; forgetting therefore never prevents a stuck key and only turns a key-up that does arrive into a lone key-up (KS-06 status). The non-elevated case (an elevated foreground window hides key-ups from a medium-integrity hook: README.md:911-914, `book/src/build-and-run.md:278`; (unverified) in Microsoft Learn) is no different: the press after the lost key-up reads as a repeat either way, and only its release changes, from a lone key-up to a swallowed one. So no elevation query is needed (Question 3).
**Rejected.** Keep forgetting in a non-elevated daemon (a token query at startup, and the lone key-up stays, for no gain); forget only after a focus change into a higher-integrity window (needs `OpenProcessToken` on the foreground process, which a medium-integrity daemon cannot open).
**Cost.** None; a loop over 256 entries per focus change disappears.

### D3: Open question 9 (owner): the press after Win+L fires
**What.** Swallowed case: the `SessionUnlocked`/`DesktopSwitched` reset (D1, D7) clears `active` of a swallowed held key and keeps its record, so its next key-down is a first press and fires; a non-repeating binding fires once. Passed case: the same reset re-reads the OS; Windows saw the key-up on the secure desktop, so the key is up and its next key-down is a first press. Both are pinned by scenarios (C11) and by the request-path test (C18).
**Why.** The reset is the one moment we know input went elsewhere. For passed keys the OS state is the witness: a key-up delivered on the Winlogon desktop also clears the key in the state that `GetAsyncKeyState` reads on the default desktop (unverified; manual M2 checks it). `GetAsyncKeyState` "fails" (returns 0) when "the current desktop is not the active desktop" (Microsoft Learn), so a reset that runs while Winlogon is still the input desktop reads every passed key as up: harmless for lost keys; a key really held then reads as up, and its next repeat is a first press of a key that passed (no binding swallowed it). The `DesktopSwitched` event of the switch back to the default desktop (unverified that it reaches an out-of-context hook of that desktop; M1, M5) re-reads them.
**Rejected.** (a) A per-repeat OS check on the hook path for passed keys (the roadmap follow-up, `roadmap.md:808`): the daemon's own `PressKey` of a physically held key, and any other injector, make the OS see that key up while it is held, so the next real repeat would read as a fresh press (an `LShift` `DoubleTap` would fire on a held Shift); it also adds a Win32 call per repeat. (b) A time-gap heuristic (a key-down of a held key later than the typematic delay = new press): FilterKeys can stretch the delay arbitrarily, and a key held while another key repeats gets no repeats, so the threshold has no safe value.
**Cost.** None on the key path. Residual: a swallowed key held through the lock screen and still auto-repeating after the unlock (it must be the last key pressed, held across the unlock) reads its first repeat as a press and can fire once more: new known-issues row 76 (Question 4).

### D4: A reload is one main-thread request: swap and reset between two events
**What.** `config-watcher` parses on its thread (unchanged) and hands the list to an `ApplyReload` sink:
```rust
// src/hook/config_watcher.rs
pub(crate) trait ApplyReload: Send + Sync + 'static { fn apply(&self, bindings: Vec<Binding>) -> Result<(), MainThreadError>; }
impl<T: ApplyReload + ?Sized> ApplyReload for &'static T { .. }   // the watcher tests pass leaked_hook(): &'static KeyboardHook
#[cfg(test)] impl ApplyReload for KeyboardHook { /* update_bindings; Ok(()) */ }   // test-only: the daemon has no reload without a reset
pub(crate) fn spawn_watcher(config_path: PathBuf, sink: impl ApplyReload) -> notify::Result<RecommendedWatcher>  // was pub
fn reload_into(config_path: &Path, sink: &dyn ApplyReload)
// src/hook/main_thread.rs
enum Request { SetEnabled { enabled: bool, reply: SyncSender<bool> }, Reload { bindings: Vec<Binding>, reply: SyncSender<()> } }
impl MainThreadHandle { pub(crate) fn reload(&self, bindings: Vec<Binding>) -> Result<(), MainThreadError> }  // try_send, wake, recv_timeout(REPLY_TIMEOUT)
impl ApplyReload for MainThreadHandle { .. }
impl MainState { pub(crate) fn reload(&mut self, hook: &KeyboardHook, bindings: Vec<Binding>) }  // hook.update_bindings(bindings) (sort, store, cancel_actions), then self.reset_engine(ResetReason::Reloaded)
```
`serve` answers `Reload` with `reply.try_send(())` after `with_main(|m| m.reload(hook, bindings))`. `App::run` passes `main.handle()`. Outcomes logged by `reload_into` on the watcher thread: `Ok` → `[INFO] config reloaded (N bindings live)` (unchanged); `NoAnswer` → `[WARN] config reload: the daemon's main thread did not answer within 2 s; the new bindings go live when it does`; `ShuttingDown` → `[INFO] config reload skipped: the daemon is shutting down`; `Busy` → `[ERROR] config reload failed: the daemon is busy; try again` + `[INFO] keeping previous bindings live`.
**Why.** A swap on the watcher thread followed by a separate reset leaves a window in which a key-up is decided with the new list and the old pending press, which fires the old action (the acceptance line). On the main thread, between two events, swap and reset are atomic with respect to every key event (`MainState` is reached only through `with_main`, `main_thread.rs:100-111`). `update_bindings` stays the only publisher (R7); it already cancels the executor epoch, so `reload` calls `reset_engine`, which does not cancel again.
**Rejected.** Swap on the watcher thread + a separate reset request (race above); reset first, swap later (a key-down between them arms from the old list).
**Cost.** One sort (tens of bindings, µs) and the drop of the old list on the main thread per reload; the watcher thread blocks ≤ 2 s on the reply.

### D5: Rule L and the lone key-up of KS-06
**What.** While remapping is on, a key-up passes iff its key's latest key-down passed (`mod.rs:754-760`, unchanged); with D1 and D2 nothing erases a `Suppressed` record except that key's own next key-down (`mark_blocked`/`mark_passed`) or key-up (`take_blocked`). The harness gets `Scenario::check_no_lone_key_up()` (fails when a key-up passes while the modelled OS has that key up, remapping on) and a property mode that runs it with focus changes, lost key-ups and unlocks.
**Why.** Whether a given program acts on a lone key-up (PrintScreen, `VK_APPS`: unverified) does not matter once none reaches Windows. Residual: while remapping is off the hook passes every event unread (`keyboard_hook_callback.rs:325-331`), so a key swallowed before `swch off` and released while off still gives Windows a lone key-up (row 59, kept; the off path stays the fast gate pinned by `remapping_off_keyboard_callback_returns_before_it_times_itself`).
**Rejected.** Reading the event while off to swallow such key-ups: breaks the 2.2 fast gate and the "remapping off passes untouched" contract.
**Cost.** None.

### D6: The control window
**What.** New `src/hook/control_window.rs`, main thread only (`!Send`: it holds an `HWND`):
```rust
pub(crate) struct ControlWindow { session: Option<SessionNotifications>, window: OwnedWindow, class: RegisteredClass } // field order = drop order
struct RegisteredClass { hinstance: HINSTANCE }            // Drop: UnregisterClassW(CLASS_NAME, Some(hinstance)), warn on error
struct OwnedWindow(HWND);                                   // Drop: DestroyWindow, warn on error
struct SessionNotifications(HWND);                          // Drop: WTSUnRegisterSessionNotification, warn on error
const CLASS_NAME: PCWSTR = w!("key-switch-rs control");
impl ControlWindow { pub(crate) fn create() -> windows::core::Result<Self>; #[cfg(test)] pub(crate) fn hwnd(&self) -> HWND; #[cfg(test)] fn has_session_notifications(&self) -> bool }
unsafe extern "system" fn control_window_proc(hwnd: HWND, msg: u32, wparam: WPARAM, lparam: LPARAM) -> LRESULT;
fn session_change(wparam: WPARAM) -> Option<ResetReason>;   // Some(SessionUnlocked) only for WTS_SESSION_UNLOCK
fn session_ends(wparam: WPARAM) -> bool;                     // WM_ENDSESSION: wParam != 0
```
`create`: `GetModuleHandleW(None)` → `RegisterClassW(&WNDCLASSW { lpfnWndProc: Some(control_window_proc), hInstance, lpszClassName: CLASS_NAME, .. })` (0 → `Error::from_thread()`, for example `ERROR_CLASS_ALREADY_EXISTS`) → `CreateWindowExW(WS_EX_TOOLWINDOW | WS_EX_NOACTIVATE, CLASS_NAME, w!("key-switch-rs"), WS_POPUP, 0, 0, 0, 0, None, None, Some(hinstance), None)` (not visible, no taskbar or Alt+Tab entry, never activated; top-level, so it receives broadcasts, which message-only windows do not) → `WTSRegisterSessionNotification(hwnd, NOTIFY_FOR_THIS_SESSION)`. Its failure (`RPC_S_INVALID_BINDING` before Remote Desktop Services have started) is not fatal: `[WARN] could not register for session notifications (…); an unlock resets the state through the desktop switch only`, `session = None`. A partial failure drops the guards already made.
Window procedure: `WM_WTSSESSION_CHANGE` → if `session_change` gives `Some(r)` and `get_hook().is_enabled()`, `main_thread::request_reset(r)`; returns 0. `WM_QUERYENDSESSION` → `LRESULT(1)`. `WM_ENDSESSION` with `session_ends` → `get_hook().uninstall()` (warn on error), `[INFO] the session is ending; removing the keyboard hook and exiting`, `logging::flush()`, `PostQuitMessage(0)`; returns 0. `WM_CLOSE` → 0 (ignored: only the Drop guard destroys the window). Anything else → `DefWindowProcW`. Nothing in it can panic.
`App::run` (`src/core/app.rs:201-202`): right after `MainThread::new()`, `let _control = ControlWindow::create().map_err(|e| format!("could not create the control window: {e}"))?;` (fatal, before any hook), then `main.refresh_foreground()` (D9). Declared before `AttachedExecutor::attach` (`app.rs:207`), so on every return it drops after the `AttachedExecutor` guard (executor stopped) and after the explicit `uninstall` (`:224`, `:277`), on the main thread.
`MAIN_WAKE` stays a thread message (`main_thread.rs:67`, `:349-355`): Question 1.
**Why.** Spec; message-only windows "do not receive broadcast messages" (Microsoft Learn), and `TaskbarCreated` is a broadcast. `WTSRegisterSessionNotification`: "When a window no longer requires these notifications, it must call WTSUnRegisterSessionNotification before being destroyed", so the session guard drops first. `UnregisterClassW` fails "if a window still exists that was created with the class", so the class guard drops last. `DestroyWindow` must run on the creating thread: `!Send`, created and dropped in `App::run`. `WM_ENDSESSION`: "the session can end any time after all applications have returned from processing this message", so the hook goes and the log is flushed inside the handler; the flush (≤ 1 s) runs outside `with_main` and off the hook path, with the hook already removed, so no keystroke waits for this thread.
**Rejected.** A subclassed `STATIC` window (no `Gdi`/`LibraryLoader` features, as `bench.rs:492-503` does): a system control class with a replaced procedure is a test trick, not a window the tray can own. A message-only window: no broadcasts. The window inside `MainThread::new()`: every test that makes a main thread would own a top-level window that must pump, or broadcasters using `SendMessage` wait on it.
**Cost.** Two features of the existing `windows` crate (compile time only), one window, one class. The main thread now also gets broadcasts (`WM_SETTINGCHANGE` and the like), each a `DefWindowProcW` call, rare.

### D7: Unlock and desktop-switch resets are main-thread requests
**What.** `src/hook/main_thread.rs`:
```rust
thread_local! { static PENDING_RESET: Cell<Option<ResetReason>> = const { Cell::new(None) }; }
/// Main thread only (window procedure, WinEvent callback): the loop resets at its next drain.
pub(crate) fn request_reset(reason: ResetReason)   // PENDING_RESET.set(Some(reason)); PostThreadMessageW(GetCurrentThreadId(), MAIN_WAKE, 0, 0), result ignored
pub(crate) fn take_pending_reset() -> Option<ResetReason>   // pub(crate) for the adapter's tests
impl MainState { pub(crate) fn reset_transient_state(&mut self, hook: &KeyboardHook, reason: ResetReason); fn reset_engine(&mut self, reason: ResetReason) }
```
`reset_engine`: if `reason.may_have_lost_key_events()` → `self.foreground.resync()` (D9, from C17); `let env = HookEnv::new(&self.foreground)`; `self.engine.reset(&env, reason)`; `self.timers.retain(live)`. `reset_transient_state` = `reset_engine` + `hook.cancel_actions()`. `set_enabled(&mut self, hook, enabled) -> bool` (no `env` parameter any more) calls `reset_transient_state(hook, RemappingSwitched)` on a real change.
`drain` (`main_thread.rs:484-499`): requests, then `take_pending_reset()` → `with_main(|m| m.reset_transient_state(hook, r))` and, for `SessionUnlocked`/`DesktopSwitched`, `[INFO] state reset: {r}` (logged after the borrow), then due timers; the reset counts as work for the "busy" pass. `MainThread::new()` and `Drop for MainThread` clear `PENDING_RESET`.
WinEvent: `KeyboardHook` gets `desktop_hook: AtomicPtr<c_void>`; `install` (`keyboard_hook.rs:132-184`) adds `SetWinEventHook(EVENT_SYSTEM_DESKTOPSWITCH, EVENT_SYSTEM_DESKTOPSWITCH, None, Some(keyboard_hook_callback::desktop_switched), 0, 0, WINEVENT_OUTOFCONTEXT | WINEVENT_SKIPOWNPROCESS)` after the foreground hook; an invalid handle → `uninstall()` and `Err(E_FAIL, "SetWinEventHook failed for EVENT_SYSTEM_DESKTOPSWITCH")`, as for the foreground hook. `uninstall` (`:196-220`) unhooks it first (`swap(null, AcqRel)`, warn `could not remove the desktop-switch hook: …`). `desktop_switched` (in `keyboard_hook_callback.rs`): returns if `!hook.is_enabled()`, else `request_reset(DesktopSwitched)`; it names no `log::`.
**Why.** Spec ("as a request served by the main thread (the 2.2 request queue and MAIN_WAKE)"). Both callers run on the main thread, so a `SyncSender` detour adds a capacity failure and nothing else; the cell coalesces the unlock notification and the desktop switch of one unlock into one reset. The reset itself always runs in the drain, never inside a callback (a sent `WM_WTSSESSION_CHANGE` or a WinEvent could otherwise be dispatched inside another callback's message call). The posted `MAIN_WAKE` makes the wait return even if the callback ran inside `MsgWaitForMultipleObjectsEx` (whether that dispatches is undocumented; 2.2 results, "Positives"). `UnhookWinEvent` "fails if called from a thread different from" the installer, so both hooks stay in `install`/`uninstall` on the main thread (KS-01). Skipped while remapping is off: the `swch on` reset resyncs anyway, and the off path does nothing (2.2 contract).
**Rejected.** `Request::Reset` through the `SyncSender` (capacity 8: a full queue loses the unlock reset); a reset directly in the window procedure (runs inside whatever message call dispatched it); one WinEvent hook over `EVENT_SYSTEM_FOREGROUND..EVENT_SYSTEM_DESKTOPSWITCH` (3..0x20 includes capture start and end on every click, move/size and menus: extra wakes of the hook thread).
**Cost.** One more WinEvent hook (events only on desktop switches); one `Cell` read per drain.

### D8: Session end
`WM_QUERYENDSESSION` returns TRUE ("Applications should respect the user's intentions and return TRUE"); `WM_ENDSESSION(TRUE)` as in D6. No `ShutdownBlockReasonCreate`. The console `CTRL_CLOSE_EVENT` handler (`app.rs:306-333`) is unchanged.

### D9: Foreground cache: exe name per (HWND, pid), title read live
**What.** New `src/platform/foreground.rs` (no crate imports outside tests):
```rust
pub trait WindowQuery {
    fn foreground(&self) -> HWND;                      // GetForegroundWindow
```

### D10: OQ2: a passing multi-key DoubleTap is not cancelled by its own keys
**What.** `Gestures::other_key_down(vk: VIRTUAL_KEY, ..)` (was `u16`; the caller `mod.rs:559-560` passes `vk`): a press in `Phase::AwaitSecond` is skipped (neither cancelled nor its waiting Tap fired) when a key of its own group accepts `vk`: `group.keys.keys.iter().any(|k| k.accepts(vk))` (`KeySpec::accepts`, `key_spec.rs:134-139`; `AnySide` covers both sides and the generic code, R8). `Phase::Held` is unchanged: re-pressing an own key of a held combo re-arms the group under that key (`press`, `gestures.rs:165-229`), so the old press is replaced, not doubled.
**Why.** Reviewer OQ2 and the spec. Exempting held presses would leave two pending presses of one group (the old one under Shift, a new one under Ctrl), and both Holds could fire. ≤ 4 `accepts` per waiting press per first key-down; no allocation.
**Rejected.** A `[u64; 4]` own-key set stored per press: not needed, `AwaitSecond` already holds `GroupKey.keys` (`gestures.rs:78-84`).
**Cost.** Negligible. The second press completes only in the order that arms the group under the same key (Ctrl, then Shift, for a press armed under Shift); the other order ends the window (documented in §11.4).

## Risks and edge cases (R1-R10)

- **R1 hook callback and engine.** Under the borrow the callback may now read a title (`GetWindowTextW`, other processes only: no message, non-blocking by design) and never queries a process; no allocation is added on the key path (`AppEquals` loses one). `code < 0`, the off gate, sentinel-first and the one-outcome rule are untouched. `other_key_down` takes `VIRTUAL_KEY`, so the engine builds no `VIRTUAL_KEY(raw)`. Re-entry: a `WM_WTSSESSION_CHANGE` or WinEvent dispatched inside another message call only sets a cell (D7); `foreground_changed` under a refused borrow updates nothing (as today).
- **R2 sentinel.** No new `SendInput`.
- **R3 shared state.** `desktop_hook` is atomic; `PENDING_RESET` and `MainState.foreground` are main-thread locals; no new lock. `install`/`uninstall` stay on the main thread (`WM_ENDSESSION` calls `uninstall` there).
- **R4 orderings.** `desktop_hook`: `store(Release)`, `swap(AcqRel)`; nothing `Relaxed` or `SeqCst`.
- **R5 builders.** No setters; `ForegroundCache::with_query` is test-only.
- **R6 Display.** `ResetReason` gets four arms; `Request::Reload` needs none (private).
- **R7 specificity.** The reload path still publishes through `update_bindings` (sort + store); the test-only `ApplyReload for KeyboardHook` does too.
- **R8 key identity.** Own keys use `KeySpec::accepts` (left, right, generic); the reset resyncs by raw code, as today.
- **R9 process reads.** The same rights and call as `condition.rs:189-223` (`PROCESS_QUERY_LIMITED_INFORMATION`, native image name, `Owned` handle); the 512-unit title buffer is kept; reads only.
- **R10 loop and shutdown.** The window is created before `install` and destroyed after `uninstall` on the main thread; `WM_ENDSESSION` removes the hook before its ≤ 1 s flush; a late watcher reload gets `ShuttingDown` after `drop(main)` (`app.rs:274`).
- **Repeats.** A key held through an unlock and still repeating reads one repeat as a press (D3, row 76). A reload keeps the held keys' records, so repeats stay repeats.
- **Sided modifiers.** Matching unchanged; the reset writes generic codes only from the OS (as `reset_from_os`).
- **Reload mid-gesture.** Dropped by design (row 77); the key-up of a swallowed press stays swallowed.
- **`swch off/on` during a gesture.** The drop is unchanged; a swallowed key released while off still gives a lone key-up (row 59).
- **Foreground race.** A key decided before the `EVENT_SYSTEM_FOREGROUND` of a focus change that just happened sees the previous window's exe name (master read `GetForegroundWindow` live). The main thread runs at `THREAD_PRIORITY_HIGHEST`, so the window is the event's delivery latency unless the thread is busy (the relative order of a WinEvent and a later low-level hook call in one wake is undocumented: unverified). M3 checks Alt+Tab with an immediate key. Follow-up F3.
- **Missed foreground events.** None documented for top-level windows ("The system sends this event even if the foreground window has changed to another window in the same thread"); every lost-input reset re-reads the foreground anyway.
- **UIPI.** `TaskbarCreated` from a medium-integrity Explorer to the elevated window will need `ChangeWindowMessageFilterEx` in 4.6 (F2).
- **Tests creating windows.** Only the control-window test creates a top-level window, briefly, under a test mutex; every other window in the tests stays message-only.

## Questions for the orchestrator

1. `MAIN_WAKE` stays a thread message; the window handles only window messages (spec: "the WM_APP_* messages go through it"). Recommendation: accept. The main thread runs no modal loop, so the documented loss of thread messages in modal loops cannot occur; a window target would make every `MainThread::new()` (dozens of tests) own a top-level window that must pump; `MAIN_WAKE` is pinned by `a_message_posted_behind_a_wake_is_dispatched_without_more_input`. 4.6's tray callbacks will be window messages of this window.
2. A reload resets gestures, chords, sequences, the owed mask and the timer generation, but not the key table (spec: "resyncs all 256 keys"). Recommendation: accept (D1): no key event is lost on a reload, and the OS resync races a key-down that just passed, which can leave a key stuck in Windows.
3. A foreground change stops forgetting swallowed key-downs in every daemon, not only an elevated one. Recommendation: accept (D2): forgetting never prevents a stuck key in the current engine; dropping it everywhere avoids a token query and a second behaviour.
4. A swallowed key held across the lock screen and still auto-repeating after the unlock reads its first repeat as a press (new known-issues row 76). Recommendation: accept as documented: that key must be the last one pressed and held through the whole unlock; preventing it needs the time-gap heuristic rejected in D3.
5. `WM_ENDSESSION(TRUE)`: remove the keyboard hook, log one line, flush the log (≤ 1 s), post `WM_QUIT`. Recommendation: accept; `daemon.log` gets a last line, and 4.2 builds on it.
6. Three `windows` features (`Win32_Graphics_Gdi`, `Win32_System_LibraryLoader`, `Win32_System_RemoteDesktop`); the roadmap names only the last. Recommendation: accept: features of an existing dependency, `Cargo.lock` unchanged; `RegisterClassW` and `WNDCLASSW` are gated on `Win32_Graphics_Gdi` in `windows` 0.62.2.
7. R9 and R10 have no `master` number; their baseline is commit C15. Recommendation: accept; the tester runs the bench on master, C15 and HEAD.
8. For the owner report: titles are read per key-down (one non-blocking call) rather than kept current through `EVENT_OBJECT_NAMECHANGE`. Recommendation: accept (D9); it is cheaper than master's path and needs no extra hook.
