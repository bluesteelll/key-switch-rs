## Important (must be resolved; options may be discussed)

### I1. "Drain before every GetMessageW" does not hold after step 2: a job submitted while a resumed macro's `OpenUrl` step pumps messages loses its `WAKE` and waits for an unrelated wake
Where: cut.md:91-94 (loop steps 1-4), :96 (Producer side: "the executor drains before every `GetMessageW` ... a drain that misses the job is followed by a queued `WAKE` (no lost wakeup)"), :97 (D2 Why: PostThreadMessage messages "will be lost" in a modal loop, "a ShellExecuteW error dialog"), :99 (D2 Cost), :502 (Risks "Blocking steps": "wake and timer messages a modal loop swallows are harmless (drain-before-wait; ...)"); code `src/data/sequence.rs:50-55` (`Launch`/`OpenUrl` are macro steps), `:131-132`, `src/core/windows_actions.rs:259-282` (`shell_open` -> `ShellExecuteW(None, ..)`).
Problem: the loop drains the channel only in step 1. Step 1 is safe on its own: after every `start(job)` + `poll()` it repeats `try_recv`, so a `WAKE` eaten during an action costs nothing. Step 2 is the gap. It runs `runs.poll()`, which calls `runner.step` for every due run. This is the normal path after a `WM_TIMER`, because step 1 then finds the channel empty and polls nothing. Steps include `OpenUrl` and `Launch` (`sequence.rs:50-55`). After step 2 the loop goes to step 3 (`arm`) and then step 4 (`GetMessageW`), with no `try_recv` in between. Only `Due` goes back to step 1. If the step pumps the thread's queue (the modal loop the cut itself names in D2 Why and Cost), a `WAKE` posted by a `submit` meanwhile is removed and dropped. PostThreadMessageW, Remarks: "if the recipient thread is in a modal loop (as used by MessageBox or DialogBox), the messages will be lost" (https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-postthreadmessagew). ShellExecuteW's `hwnd` is "the parent window used for displaying a UI or error messages", and its error codes include DDE transactions (https://learn.microsoft.com/en-us/windows/win32/api/shellapi/nf-shellapi-shellexecutew). The job then sits in the channel while the executor blocks in `GetMessageW`. The `Due` check after the poll does rescue lost `WM_TIMER`s (deadlines are re-read from `Instant`), but nothing rescues the channel.
Consequence: take `( keys: "F16", action: Sequence([ Delay(100), OpenUrl("<a target whose ShellExecuteW shows UI or pumps>") ]) )` and `( keys: "F13", action: OpenUrl("https://example.com") )`. Press F16. 100 ms later the run resumes in step 2's poll, and `ShellExecuteW` runs its dialog or DDE/COM wait. Press F13 meanwhile. Its job is queued (the declared cost) and its `WAKE` is eaten. Then dismiss the dialog. The F16 run ends, `arm` returns `Idle`, and the executor waits in `GetMessageW`. The browser never opens for F13. It opens only when the user presses some other `Launch`/`OpenUrl`/`Sequence` hotkey, and then both run at once. If another macro is waiting in a `Delay`, F13 runs late, when that timer fires. Before the lane, F13 opened at once. The user sees a hotkey that silently does nothing: no counter moves and `swch status` says `running`. This is the R3 kind of silent failure, from a path the cut calls "harmless". `swch off`, reload and exit are not affected: `live` is checked before every step, and `stopping` after every poll.
Confidence: CONFIRMED that the plan has the gap (cut.md:91-94 against :96 and :502). The trigger, a pump inside `ShellExecuteW`, is the cut's own premise (cut.md:97, :99, :502).
Breaks: D2's no-lost-wakeup invariant; KS-08 intent (a slow action must not be held up beyond the step that is running); the R3 visibility spirit.
What is needed: the last call that can pump messages before `GetMessageW` must be followed by a channel drain, or by an equivalent producer-side "pending" signal that a modal loop cannot eat. The cut's claim at :96 and :502 must then be true as written. Add a test that pins it with no hook and no injection: a fake step removes the executor thread's own posted messages (a stand-in for a modal loop) while the test submits a job, and the job must run promptly after the step returns, with no other wake.

### M2. M11 may not reproduce the hang it is meant to show: the foreground "(Not Responding)" window can be DWM's ghost
Where: cut.md:490 (M11: "wait until its title shows '(Not Responding)' ... with the synchronous `ShowWindow` it would open only after the window recovers").
Problem: the "(Not Responding)" title belongs to window ghosting. Microsoft describes ghosting as the feature that "lets the user minimize, move, or close the main window of an application that is not responding" (https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-disableprocesswindowsghosting). Per that description, the window the user then interacts with is a stand-in that stays responsive. If `GetForegroundWindow()` returns the ghost when F19 is pressed, the target is a responsive window. A synchronous `ShowWindow` on it would return at once too.
Consequence: M11 can pass with the round-1 code. The manual check then shows only that the URL opens, not that a hung target no longer blocks the executor. X3's scan still pins the code change. M11's stated contrast ("it would open only after the window recovers") could be false.
Confidence: PLAUSIBLE (Microsoft does not document whether `GetForegroundWindow` returns the ghost).
What is needed: either make the hung window's own HWND the target (for example with ghosting off in the test process, so its title never changes), or drop the contrast claim and say what M11 does prove.

### M3. "Equal deadline -> Waiting" trusts the armed periodic timer, so a `WM_TIMER` lost just before its deadline costs the run a whole period
Where: cut.md:123 (`arm`: "`At(t)` equal to the armed `for` -> `Waiting`"; `fired`: "the next `arm` re-arms from `Instant`, so an early, late, stale or periodic repeat `WM_TIMER` corrects itself"), :504 (Timer details).
Problem: the self-correction runs only when *our* loop retrieves the `WM_TIMER` and calls `fired`. Say the timer's message comes slightly before `t` by `Instant`: user timers count down on clock ticks, so they can arrive up to about one tick early. If a foreign modal loop eats that message, either in a concurrent run's `OpenUrl` step (as in I1) or inside step 4's `DispatchMessageW`, and returns before `t`, then the next `arm` sees the same `for`, returns `Waiting` and keeps the old timer. A `SetTimer` timer is periodic, so its next `WM_TIMER` comes one full `uElapse` later.
Consequence: a `Delay(10000)` macro resumes at about 20 s instead of 10 s, if another macro's `ShellExecuteW` was pumping in the narrow window just before its deadline. The window is narrow (one tick), and a `Delay` still never ends early.
Confidence: PLAUSIBLE (early tick delivery is not documented; the shortcut is CONFIRMED in the plan).
What is needed: a lost-before-deadline `WM_TIMER` must not cost more than about one tick. For example, the timer's state must not be trusted after foreign code has pumped the queue. Whatever fixes I1 may be the natural place for this.

## Strengths to keep
- Time is decided by `Instant`, not by timer messages. Every `WM_TIMER` of ours kills the timer and forgets it. The `Due` check after every poll means an early, late, stale, reused-id or modal-loop-eaten `WM_TIMER` never makes a `Delay` end early, and a deadline that passed during a blocking step is caught at once. `timer_ms` clamps to `USER_TIMER_MAXIMUM`, and the kill-then-create approach never trusts a reused id (the SetTimer and SetCoalescableTimer Remarks).
- No callback of ours lives on the executor thread: no `TimerProc` and no window. So no message pump, whether COM's, a dialog's or a foreign window procedure's, can re-enter `Runs` or `DelayTimer`, and Rust's `&mut` makes that structural. The STA re-entrancy question reduces to message loss, which is I1 and M3.
- `live` (epoch + `stopping`) is checked at dequeue, at the start of every poll and before every step, so `swch off`, reload and exit work even when their `WAKE` is lost. `stopping` is also checked after every job and every poll, so stop is robust to a modal loop.
- Starvation is bounded. Jobs are drained before runs, every job is followed by a poll, a `Delay(0)` run advances once per poll, and the `Due` spin ends once no deadline is due. Order is deterministic: age order, with deadlines taken when the `Delay` step is reached. R-b and X1-4 pin exact sequences that one-at-a-time execution would fail.
- A panic is caught per runner call, and a step's panic ends only its macro (R-f, X1-17). A loop panic is a counted death.
- The pure `runs.rs` has a fake clock and covers R-a..R-h. Every new real-thread test uses a FakeRunner, and only the `Win32Runner` test is `#[ignore = "manual: ..."]`.

## Open questions for the architect
1. Loop-panic death (D14): the epilogue drains and counts the queue "before it drops the receiver". That works only if the receiver, and the `DelayTimer`, live outside the closure that unwinds. No test covers this path; X1-16 covers `WM_QUIT` only. To settle it, state where they are owned, or accept that a loop panic loses up to 32 queued jobs uncounted.
2. N3 (default coalescing): X1-6's 1 s bound and M5 judged by eye cannot tell `thread::sleep`'s ~15.6 ms lateness from a few hundred ms. A manual timing line would settle N3 before users report slow macros, for example `Sequence` of 20 x `[Key("F13"), Delay(50)]` finishing in about 1.0-1.4 s.
3. `ShowWindowAsync(SW_RESTORE)` on a *minimised* window: the restore, and any activation, now run on the target's own thread, under that process's foreground rules. Whether `[Window(Minimize), Delay(2000), Window(Restore)]` still brings the window to the front is unverified. No published example does this: the README and example macros restore the window that was foreground when the binding fired. One manual try settles it; if it changed, add it to the X4 `Changed` entry.
